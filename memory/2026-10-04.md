## 列数在重启后退化为假设值（第三轮修复）
用户实测：设「每行5个」，**重启 explorer 后只显示 4 列**，末项被挤到下一行且右侧留白；重新安装新构建包又恢复正常。

### 为什么前两轮修复都没解决
- 第一轮（`1cb083d` 前）只按工作区宽度封顶窗口 → 宽度不足导致少一列。
- 第二轮（`1cb083d`）加了"按可用宽度回推fitColumns"→ 只在**工作区真的放不下**时才收缩，数学上验证过是安全的。
- 真正原因：**LVS_ICON / LVS_SMALLICON 下每行项目数由 ListView 自行决定**，输入是：客户区宽度 + `LVM_SETICONSPACING` 的 cx + **标签文字实际宽度**。代码却一直用固定 `cellCx` 公式估算 cellCx，标签一长（或字体被用户放大/DPI 变化）就估不准 → 每行少放一个。
- 这解释了"重启后异常、重装后正常"：重装会重建窗口并重置字体状态，而重启是复用已有状态，偏差被固化。

### 本轮修法：闭环校正（不依赖公式推算）
提交 `fcb8701`，云构建 run `37174374246` success。
1. `LauncherGroups_MeasureAppsLabelWidth`：用 `group->hFont` + `DrawTextW(DT_CALCRECT)` 实测最宽标签（取前 8 项），作为 cellCx 下界。
2. `LauncherGroups_AlignColumnsToSetting`（核心）：填完项目后用 `ListView_GetItemRect` 实测「第 columns 项是否已换行」；若换行，按实测 `rcSecond.left - rcFirst.left` 反推真实列占位，加宽窗口并重排，最多 4 轮。
3. `GetAppsIconLayout` 增加 `labelWidth` 参数：`cellCx = max(原基准值, 标签实测宽 + 余量)`。
4. 调用时机：`UpdateAppsWindow` 内，必须在插入项目 → `LVM_SETICONSPACING` → `ResizeAppsListView` → `UpdateWindowSize` **之后**。

### 关键 API 语义（查官方文档确认，别再猜）
`LVM_SETICONSPACING` 的 lParam cx/cy **相对于图标位图左上角，必须包含图标宽度**（官方 Remarks 明确："values must include the size of the icon, plus the amount of empty space desired"，不含图标宽会重叠）。
→ 我一开始误以为"每项占位 = 图标宽 + 间距"，据此做的模拟全部 FAIL，属于**基于错误假设推演**。教训：涉及 Win32 控件布局的语义，先查文档再写模拟验证。

### 方法论教训（本轮最重要）
1. **闭环 > 推算**。控件内部布局（ListView 换行、网格换行等）由多重输入决定且可能随环境变化，与其精确推公式，不如"设置→实测→修正"的反馈环。
2. **"装上正常、重启异常"这个现象本身就是线索**：指向状态复用/初始化时序，而非单次计算错误。之前两轮都当成"宽度算错了"来修，方向就偏了。
3. 我在前两轮连续引入"宽度封顶"这类**只约束单一维度**的改动，破坏了"宽度 ↔ 列数 ↔ 标签宽"三者的自洽关系。**改动排版相关代码时，必须同时检查所有依赖该尺寸的下游计算。**
4. 用 Python 模拟 ListView 布局来做"验证"是不可靠的——模拟基于我对 API 语义的假设，假设错则结论全错（本次即如此）。模拟只能验证自己的逻辑，不能替代对真实 API 语义的确认。

### 遗留
- 闭环校正每轮会触发一次窗口 resize，最多 4 轮；项目数很多时可能有轻微重排开销，实测可接受（未量化）。

# 2026-10-04 下午：窗口尺寸统一 / 项目间隔 / 拖动换位

## 1. 同列数但窗口大小不一致
- **根因**：`LauncherGroups_MeasureAppsLabelWidth` 按**每个分组各自**实测最宽标签 → `cellCx` 因组而异。图一标签短（QQ、微信）格子窄，图二标签长（cc-switch.exe、windsurf-account-manager）格子宽。
- **修法**：新增 `LauncherGroups_RecalcGlobalCellWidth()`——在 `CreateWindowsForLoadedGroups` 里所有窗口就绪后遍历全部分组取全局最宽标签，存入 `g_launcherGroupsGlobalLabelWidth`，再统一重排所有窗口。

## 2. 项目间隔自定义
- 菜单 ID 段 **2180-2183**（SPACING_UP/DOWN/RESET/CUSTOM），与 VIEW(2120-2123)、ARRANGE(2140-2143)、FONTSCALE(2160-2163)、REMOVE(2200+) 均不重叠。
- 注册表值 `LauncherGroupsItemSpacing`（默认 100，范围 50-300）。实现：`cellCx/cellCy += MulDiv(cellCx - iconSize, spacing-100, 100)`，并设下限不小于图标宽。

## 3. 任务栏分组拖动换位
- **关键机制**：分组顺序由注册表子键的**枚举顺序**决定（`RegEnumKeyExW` 顺序遍历），键名格式 `Group%08X`（递增十六进制）→ **改键名即可改顺序**；显示名取子键下`Name` 值，故改名不影响用户可见名称。
- `LauncherGroups_SwapGroupOrder`：构造目标顺序 → 全部改临时名 `~EP_TMP_n` → 按目标顺序改回。两阶段避免互相覆盖。
- 新增 `LauncherGroups_RenameRegistrySubKey`：复制值+子键 → 删源键 → 改名（`RegRenameKey` 不可用）。
- 拖动交互：左键按下记录拖动源与起点并 `SetCapture(WindowFromPoint)`；移动超 4px 后用 `FindGroupAtPoint` 反查悬停目标；`WM_LBUTTONUP` 调`FinishTaskbarDrag`。拖动分支放在 `OnTaskbarMouseMove` 的 80ms 节流**之前**，不受节流影响。

## 关键修复（自查发现，提交 13658cd）
用户要求"修完一起构建"后，我复查发现换位逻辑有三个**会损坏分组数据**的实质缺陷：
1. **数组原地压缩**：`write` 追上 `read` 后会用已改写内容覆盖尚未读取的源数据 → 键名错乱。改为写入独立 `ordered` 缓冲区，回写前校验 `write == total`。
2. **`RegDeleteKeyExW` 返回值被忽略**：删除失败时函数仍返回 TRUE，下一步因"目标名已存在"失败 → 键名重复。改为检查删除结果，失败则清理新键并返回 FALSE。
3. **第二步中途失败无回滚**：会留下半改状态（一部分新名一部分临时名）且无法恢复。改为失败时倒序把已改名键改回临时名，使注册表停留在"全部临时名"的一致状态。
- 另加固：值复制前检查 `cbData > 缓冲区大小` 并中止，避免静默截断。
- 教训：涉及**持久化数据重命名**的操作，"看起来能跑"不等于正确——必须逐条检查失败路径是否会留下损坏状态。写完主动做失败路径审查，而不是等编译通过就收工。

# 2026-10-04 下午：三问题修复（提交 82b1607，已推送，待云构建）

## 1. 项目间隔调小无响应 —— 根因是 ListView 的宽度下限
-截图实测：蓝色高亮 140×84px，最宽标签 117px；而旧公式按 spacing=80% 反推 cellCx≈109px，**对不上**。
- 差值 140-117=23px 正是"标签+内边距"。
- **ListView 图标视图会把单元格宽度下限锁死在标签实测宽度上**。
  旧写法 `gapExtra = MulDiv(cellCx - iconSize, spacing-100, 100)` 是"整体宽度百分比缩放"，
  目标宽度一旦低于标签下限，多出的差值直接被下限吃掉 → 100/90/80/70/60 五档全被截在同一位置，故"完全没响应"。
- 修法：`cellCx = contentCx + MulDiv(baseGap, spacing, 100)`，即「内容宽 + 可缩放留白」，
  cellCx 恒≥ 标签下限，两个方向都生效。纯算术可验，无需跑起来看。
- 已验算：spacing 50→300 对应 cellCx 152→312，**全程单调递增**，每档均高于下限 120px。

## 2. 任务栏分组拖不动 —— 根因是钩子的作用域
- `SetWindowsHookExW(WH_MOUSE, ..., GetCurrentThreadId())` 是**线程局部**钩子，只对本线程窗口消息可见。
- 鼠标捕获一旦转移到 XAML 任务栏按钮（另一个线程），钩子就收不到 WM_MOUSEMOVE/WM_LBUTTONUP
  → 按下有效、拖动无跟踪、松手退化成一次菜单点击，**与用户描述完全吻合**。
- 修法：改 `WH_MOUSE_LL`（全局低级钩子，threadId=0）。
- 代价与对策：全局钩子每次鼠标事件都进，入口加 `g_launcherGroupsDragActive || IsTaskbarPoint(pt)`
  廉价闸门（拖动中无条件放行，因鼠标可能已移出任务栏）。

## 3. 窗口内项目换位是死代码 —— 已在上一节确证

  1. `LVN_BEGINDRAG` 返回**非 0**，抑制 ListView 自带拖动（否则它抢回捕获）；

## 二、窗口内项目换位：真缺陷 = ReleaseCapture 同步重入
### 日志证据链（每条 up 后都紧跟一条 capture lost，毫秒数完全相同）
```
15:14:35.377 item drag up from=5 target=2 capture=0x30860
15:14:35.377 item drag capture lost newOwner=0000000000000000 from=5   ← 同毫秒
```
三次拖动（5→2、2→5、1→4）全部如此，`move item` 恒为 0 次。

### 根因
子类 `WM_LBUTTONUP` 里旧顺序是：
`ReleaseCapture()` → `group->bDragActive=FALSE` → 读 `group->iDragItem` → `MoveItem(...)`
而 `ReleaseCapture()` 会**同步**把 `WM_CAPTURECHANGED` 发回本窗口
（官方文档明确："A window receives this message **even if it calls ReleaseCapture itself**"），
该分支执行 `group->iDragItem = -1` → 重入返回后 `MoveItem` 拿到 **from=-1**，
在入口 `from < 0` 校验处**静默 return FALSE**。
→ 表现为"拖动有高亮、松手不换位"，即用户说的"无响应"。

### 修复
先把 `from` 存局部变量 → 清状态 → 执行 `MoveItem` → **最后**才 `ReleaseCapture()`。
另给 `MoveItem` 两个失败出口补日志（REJECTED / SAVE FAILED），杜绝再次静默失败。

## 关键教训（本项目最值得记住的一条）
1. **`ReleaseCapture` 会同步重入 `WM_CAPTURECHANGED`** —— 凡是"清状态 + 释放捕获"
   的代码，若状态字段被 `WM_CAPTURECHANGED` 分支清理，**顺序颠倒就会自毁**。
   本项目此前三轮都在"改行为"，本轮靠**一条埋点 + 官方文档**就定了案。
2. **静默 return FALSE 是排查黑洞**：`MoveItem` 参数非法与保存失败两条路径都不打日志，
   导致 `from=-1` 这种值被清掉的过程完全不可见。**每个 early-return 都该留证**。
3. **用户说的"哪个功能坏了"要验证而非采纳**。本例"任务栏无响应"经日志+注册表双向核对
   证明完全正常；若照用户描述去改任务栏逻辑，会白改一轮。
4. 埋点方向选对了：记录**状态字段被清空前的值**（`from=%d`）而非只记事件发生，
   一步就暴露了"值被谁改了"。
